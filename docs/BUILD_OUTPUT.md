# Вывод и журналы сборки

Обычная команда `ANK-DOCX.cmd build "Название"` и пункт меню «Собрать DOCX» показывают текущий этап и прошедшее время, а после завершения — диагностику: ошибки и предупреждения инструментов, включая рекомендации. Если замечаний нет, итоговая диагностика состоит из строки: «Ошибок и предупреждений сборки не обнаружено.»

В интерактивном терминале используется штатный индикатор `Spectre.Console.Status`: расчёты и таблицы R, создание DOCX, компоновка Word, обновление ссылок, размещение таблиц, сохранение и проверка. Для таблиц показано число обработанных объектов. Пока идёт длительная операция Word, индикатор и время продолжают обновляться. При перенаправленном выводе вместо анимации печатаются редкие строки состояния в stderr, не реже одного раза в 10 секунд. stdout и короткий журнал остаются диагностическими; `--verbose` по-прежнему показывает полный вывод инструментов.

Примерное оставшееся время всей сборки вычисляется по последней успешной сборке **этой работы**. Её длительность хранится в `.quarto/build-duration.txt`; неудачный запуск её не заменяет. Это ориентир: изменение объёма приложений, окружения или вычислений может существенно изменить время. Когда предыдущего замера нет, показываются фактический этап и время, а после нескольких обработанных таблиц — оценка оставшегося времени только текущего этапа. Если запуск длится дольше прошлого, программа прямо сообщает об этом.

Внутри работы сохраняются два UTF-8 файла:

| Файл | Назначение |
|---|---|
| `.quarto/build-summary.log` | Итоговая короткая диагностика без индикатора, времени и метаданных. Агент может прочитать её после сборки. |
| `.quarto/build.log` | Весь вывод Quarto и дочерних процессов: прогресс R, параметры, метаданные, JSON финализации и подробности ошибок. Нужен для отладки. |

Оба файла **перезаписываются при каждом запуске**, включая неудачный. Они находятся вне `_output/`, поэтому очистка результатов Quarto их не удаляет. В Git работы их добавлять не нужно: `.quarto/` уже игнорируется Starter. Меню выбора действий и работ не включается в короткий журнал сборки.

Word-worker передаёт текущие операции отдельными строками `ANK-PROGRESS` с JSON в stderr только при `ACADEMIC_BUILD_PROGRESS=1`, который устанавливает workspace build. Они сохраняются в полном журнале и исключены из диагностик. В существующий отчёт `*.finalize.json` добавлены длительности этапов `seconds`; это позволяет отличить расчёты R от обработки DOCX и найти медленную операцию без чтения всех исходников работы.

Ошибочная сборка возвращает ненулевой код завершения. Прежний DOCX может остаться на диске; это не результат нового успешного запуска. Старый `main.docx.finalize.json` удаляется перед сборкой, чтобы ошибка до финализации не объяснялась устаревшим отчётом Word.

## Подробный режим

В меню есть «Собрать DOCX (подробный вывод)». Для терминала:

```powershell
.\ANK-DOCX.cmd build "Название" --verbose
```

В этом режиме весь прежний вывод процесса виден по мере сборки и также сохраняется в `build.log`. Файл `build-summary.log` остаётся коротким. Прямой `quarto render` и служебный `tools\build-academic.cmd` сохраняют подробный вывод для разработки; новые журналы создаёт обёртка workspace build.

## Для агента

1. Используй обычную команду build, учитывай код завершения.
2. Если контекст предыдущего запуска недоступен, прочитай `build-summary.log`.
3. При необходимости прочитай существующий структурный `main.docx.finalize.json` текущего запуска.
4. Полный `build.log` читай только для расследования, когда короткой диагностики недостаточно; не загружай его при каждой штатной сборке.

Короткий вывод ограничен 30 строками диагностик; длинные трассировки остаются в полном журнале. Если сообщений больше, консоль указывает на полный файл. Без доступного исходного местоположения обёртка не придумывает файл и строку QMD.

Сервис 0.4.10 при сообщении о метке вычисляемой ячейки дополнительно использует штатный `quarto inspect`: при однозначном совпадении добавляет исходный QMD, диапазон строк и первую непустую строку кода. Это начало ячейки для ориентира, а не утверждение о строке причины ошибки. Например, knitr может сообщить строку объединённого `main.qmd`, а inspect определяет настоящую ячейку внутри `include`. Если метка неоднозначна или inspect недоступен, исходная диагностика сохраняется; файл и строки для обычных заголовков и абзацев этим способом не определяются. Inspect запускается только при подходящих сообщениях и не влияет на успешность сборки.

Сервис 0.4.11 также сопоставляет рекомендации об исполняемом листинге с ячейкой через `lst-label`. Неисполняемые листинги и формулы пока не имеют координат из `quarto inspect`.

Рассмотрен штатный [JSON-stream журнал Quarto](https://quarto.org/docs/cli/render.html). В проверенном Quarto 1.10.19 часть предупреждений имеет уровень INFO, сообщения Citeproc разбиваются на отдельные фрагменты, а некоторые ошибки Lua/Pandoc отсутствуют в этом журнале. Поэтому компактная диагностика выбирается из полных строк stdout/stderr по явным заголовкам ошибок, предупреждений, рекомендаций и остановки R. Существующий JSON-отчёт Word используется для подробной причины сбоя финализации. Отдельный анализатор QMD, новый формат отчётов и движок проверок не добавлены.

С расширением 0.4.5 сюда также попадают необязательные рекомендации о вводном тексте главы и упоминании таблиц и рисунков, с 0.4.6 — о таблицах основной части на трёх и более страницах, с 0.4.8 — об упоминании листингов и формул и некоторых ручных номерах объектов. Они не меняют код завершения сборки. Их границы и примеры описаны в [инструкции автора](AUTHORING.md). Это не оценка правильности содержания или нормативный контроль.

## Проверенные сценарии 0.4.8

Проверены предупреждения Crossref и Citeproc, ошибки YAML и настоящего Lua-фильтра расширения, кириллица в путях, возврат из обычного и подробного меню после сбоя. Повторный запуск убирает прежние предупреждения и ошибки из обоих журналов; короткий файл совпадает с обычным консольным выводом. В подробном режиме прогресс и метаданные видны в консоли, а короткий файл остаётся коротким.

Практическая с R, flextable и формулой собрана в Word: 2 страницы, 0 ошибок итоговой проверки SDK, обычная консоль — одна строка. Следующая сборка с пустым `title` остановлена с ненулевым кодом, короткая диагностика содержит имя поля и причину, устаревший отчёт успешной финализации удалён. Материалы проверок и журнал эксперимента со штатным JSON-stream находятся в игнорируемой `.tools/build-output-probe/`.

В 0.4.9 отдельно проверены синтаксическая ошибка R (`x <- (`) и ошибка выполнения (неизвестная переменная). Обе останавливают стандартную сборку с `execute.error: false`. Короткий вывод содержит причину, код при синтаксической ошибке и строку knitr с файлом, диапазоном строк и меткой ячейки. Поддержаны старый вид `Quitting from lines …` и текущий `Quitting from main.qmd:1-4 [имя]`.
