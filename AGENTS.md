# Правила исследования и дальнейшей разработки

## Сначала готовое решение

- Перед реализацией новой возможности проверь, есть ли она в стандартных средствах выбранного стека, поддерживаемой библиотеке или существующем расширении. Начинай с официальной документации и примеров; при необходимости читай исходники.
- Используй уже собранные сведения из отчётов этого проекта. Повторный поиск или эксперимент нужен при новом требовании, изменении версии, противоречии либо конкретном пробеле в доказательствах. Не начинай обзор экосистемы заново для каждой небольшой задачи.
- Предпочитай штатную настройку, готовое расширение или публичный API собственному парсеру, оператору, writer или системе плагинов. Авторский синтаксис должен оставаться документированным синтаксисом выбранной экосистемы.
- Готовый компонент оценивай по соответствию требованиям, совместимости, лицензии, сопровождению и объёму интеграции. Упоминание функции в README ещё не подтверждает нужное поведение в нашем конвейере.
- При выборе решения учитывай суммарную стоимость: работу агента над каждой работой, собственный код сборщика, возможности готовых библиотек, зависимости и будущее сопровождение. Популярность языка и число строк собственного кода по отдельности не определяют выбор.
- Если совместимость неизвестна, проведи один небольшой опыт на конкретный риск. Не пересобирай большой сравнительный стенд, когда достаточно проверить один объект или действие.
- Собственную реализацию добавляй для подтверждённого пробела. В описании изменения укажи, какое готовое средство рассмотрено, чего ему не хватает и почему выбранный объём собственного кода необходим.
- Код исследовательского стенда не считай автоматически обязательной архитектурой продукта. Удаляй лишнюю обвязку, когда её заменяет стандартный механизм.

## Текущие ориентиры

- Рабочее направление авторских исходников — Quarto и стандартный QMD. Базовый вычислительный путь первой версии — knitr и R с готовыми библиотеками Officeverse. Когда язык не является предметом работы, расчёты можно выполнять на R без добавления второго языка. Научный код Python/C++/C#/SQL-проекта не переписывай на R ради библиотеки оформления.
- Основной инструмент научных графиков — ggplot2; в DOCX используй SVG через svglite, при необходимости отдельного PNG — ragg с 600 dpi. TikZ, PGFPlots и quarto_tikz исключены из рабочего стека по решению пользователя: не добавляй их интеграцию, TeX-компиляцию или требования установки TeX. Исследовательские материалы сохранены только как история. LaTeX-разметка математических выражений в QMD остаётся: Pandoc преобразует её в OMML без TeX-компилятора.
- Разделяй служебное оформление документа, расчёты конкретной работы и исследуемый программный проект. Листинг не означает обязательное исполнение кода при сборке. Исполнение исследуемой программы внутри QMD или отдельным шагом выбирай по воспроизводимости и устройству программы, а не только по наличию такого движка в Quarto.
- Для новых работ используй единый Starter в quarto/: стандартный проект default, один chapters/main.qmd для всего содержательного текста, единые metadata.yml и academic.profile. Небольшие работы имеют ту же структуру каталогов. Book появился как заготовка Positron, а не как осознанно выбранная обязательная архитектура; он остаётся штатным вариантом для многофайловой работы и book.appendices. Не вводи собственный реестр дерева или склеивание глав. Состав сопроводительных листов задаётся профилями расширения; пока листы — явно обозначенные заглушки. Общая реализация находится в одном исходнике расширения, проекты получают установленные версии.
- knitr может выполнять Python через готовый reticulate и использовать результаты в R-таблицах, но это дополнительный вариант для конкретной работы, не обязательный путь и не приоритет первой сборки. Он ещё не проверен в полном стенде. Не вводи гибридное состояние R/Python без конкретной необходимости. Пока используется flextable, среде сборки нужен R; смена engine на Jupyter не преобразует R-код и flextable автоматически.
- Граница продукта: университетское оформление и компоновка, необходимые интеграции Word и проверка результата. Не разрабатывай новый универсальный научный редактор или конвертер без подтверждённой необходимости.
- Собственный служебный код развивай на C# с Open XML SDK и ограниченным Word COM-адаптером: docs/SERVICE_LAYER_ARCHITECTURE.md. Не возвращай Python/PS1 в поддерживаемую инфраструктуру оформления. Quarto управляет сборкой; R и Lua сохраняют штатные задачи выбранной экосистемы. Язык научного проекта этим правилом не ограничивается.
- Различай уже проверенный Quarto с нашим адаптером Word и ещё не проверенные интеграции конкретных компонентов Officeverse. Не объявляй всю связку Quarto + R + Officeverse проверенной по отдельным API.
- Отличай нативный обновляемый объект Word от статического текста. Структурное наличие OOXML, поведение в Word и сведения из документации фиксируй отдельно.
- Существующий AutoNormoKontrol используется как источник опыта. Его рабочую реализацию ради этого исследования не изменяй.
- Отсутствующие или устаревшие инструменты можно устанавливать и обновлять. Наличие ПО на текущем компьютере не определяет архитектуру; фиксируй проверенные версии и зависимости проекта.

Результаты и ограничения находятся в docs/research/: REPORT.md, QUARTO_REPORT.md, STACK_DECISION.md, QUARTO_ECOSYSTEM_AUDIT.md и EXTENSION_REPORT.md. Интеграция Quarto Book + R + flextable с OMML в ячейках подтверждена в examples/book/; это не подтверждает все компоненты Officeverse. Текущая готовая сборка требует Word: промежуточный пакет до его нормализации содержит ошибки схемы, а после сохранения Word проверенные итоговые DOCX проходят SDK без ошибок. Первоначальный RESEARCH_PLAN.md содержит исторический план, а не перечень актуально непроведённых проверок.

## Структура после исследования

- quarto/ — единый поставляемый Starter и единственный исходник расширения _extensions/academic/. Новая работа: quarto use template; содержательный текст — chapters/main.qmd, данные — metadata.yml. См. docs/STARTER_TEMPLATE.md.
- examples/book/ — сохранённый интеграционный Book; расширение и tools/academic.R устанавливаются setup из quarto/ и игнорируются Git. Команда из корня: build-academic.cmd. examples/objects/ содержит отдельные образцы.
- docs/ — план и вопросы продукта; docs/research/ — результаты проведённых опытов. Сначала читай docs/README.md, чтобы выбрать актуальный отчёт.
- tools/AcademicDocx/, tools/AcademicDocx.Core/ и tools/AcademicDocx.Tests/ — служебное приложение, переносимая обработка DOCX и проверки. Подготовка среды: setup-academic.cmd; команды: academic-docx.cmd.
- archive/ — локальный архив старых прототипов A/B/C, промежуточных сборок и загрузок. Это исторические материалы, не второй поддерживаемый конвейер. Не ищи зависимости рабочего формата в archive/ и не подключай их оттуда. Снимок перед уборкой проверен по SHA-256; подробности в archive/README.md.
